# Native Device QA Checklist

Use this checklist for release or device checks of native MAUI Blazor Hybrid behavior. These checks remain manual unless future repeated platform regressions justify one or two tiny device smoke tests with clear pass/fail evidence.

Record each run with the claim, device model, OS version, app build, scenario steps, result, and evidence. Prefer short notes plus a screenshot, video, device log excerpt, install result, or observed platform behavior when it proves the claim directly.

## Scope Boundaries

- Do not use this checklist to replay Core game rules. Core rule, phase, serialization, and instruction semantics stay covered by Core integration tests.
- Do not use this checklist to repeat Browser QA Host checks. Browser-host layout, CSS, viewport, focus, and deterministic rendered-state checks stay in the browser QA host.
- Do not expand this checklist into Appium planning, visual regression infrastructure, exhaustive platform certification, or broad exploratory QA.

## Checklist

| Claim | Device/platform context | Manual scenario | Expected evidence |
| --- | --- | --- | --- |
| Native real audio output works through the platform player. | Android and iOS device; Mac Catalyst when packaging that target. Test speaker output and at least one external or interrupted route when practical. | Start a game moment that has audio, confirm audible playback, confirm looping behavior where the track is meant to loop, toggle mute/unmute, background or interrupt audio with the OS, then return to the app. | Note or short video confirms sound is audible on the selected route, mute stops output, unmute resumes expected playback, loops do not stack, and interruption/resume behavior is acceptable. Evidence must cover playback mechanics only, not whether Core chose the semantic sound effect. |
| Native haptic feel is appropriate and only fires for progression actions. | Physical Android and iOS devices with haptics enabled; note unavailable haptics explicitly. | Advance through instruction transitions and press-and-hold submissions, then try general navigation such as tabs or option selection. | Observation note states whether progression taps and hold submissions feel timely and noticeable, whether unavailable platforms fail silently, and whether general UI interactions avoid unexpected haptics. |
| Native wake lock behavior keeps the moderator screen awake only while gameplay needs it. | Android and iOS device with normal auto-lock settings; Mac Catalyst if supported. | Enter Lobby and Dashboard, wait beyond the normal screen timeout, then leave gameplay or background the app. | Timed observation or video shows the screen stays awake in Lobby/Dashboard and the app releases or stops asserting wake behavior when backgrounded or outside active gameplay. |
| Native resume/background behavior preserves the accepted stable recovery boundary. | Android and iOS device; include at least one OS-level background/resume path and one process-kill or restart path when practical. | Start a session, reach a stable boundary, continue into in-progress phase work, background/resume the app, then separately force-close or let the OS kill the app and relaunch. | Note or screenshots show background/resume keeps usable in-memory progress, while process restart reloads the latest stable recovery snapshot and does not promise exact mid-phase transient state. |
| Native platform storage behavior persists and clears the active session through app storage. | Android and iOS device; include reinstall/update behavior when practical. | Create a session, process an input that triggers save, close and relaunch, then clear the session or app data as appropriate for the platform. | Screenshot, file/app-data observation, or log note confirms saved session recovery from app storage, no corrupt recovery after interruption, and expected cleanup after clear, uninstall, or app-data reset. |
| Native packaging/install behavior produces an installable app with required platform metadata. | Release-like Android package and iOS/Mac Catalyst build path available to the maintainer. | Install or update the app on a physical device, launch from the app icon, inspect splash/icon/permissions where the platform exposes them, and verify signing/install errors are absent. | Install result, screenshot, or build/deploy log confirms the package installs or updates cleanly, launches under the expected identity, shows expected icon/splash metadata, and requests only expected platform capabilities. |
| Native WebView rendering quirks do not break moderator-critical screens. | Android and iOS WebView hosts; Mac Catalyst when packaging that target. | Open Lobby, Role Selection, Dashboard tabs, long instruction text, input views, and any keyboard path inside the native shell. Rotate or resize only where the target platform supports it. | Screenshots or video show safe areas, viewport height, keyboard overlays, fixed action zones, scroll regions, dark theme first paint, and platform CSS behavior remain usable in the native host. Evidence should focus on native WebView host quirks, not duplicate Browser QA Host layout fixtures. |
| Native touch feel supports fast table moderation without accidental commitment. | Physical phones in portrait orientation; test one-handed use when practical. | Exercise tap selection, tab changes, scroll momentum, press-and-hold submit, cancellation by moving away, and dark-room readability during Dashboard use. | Observation note or short video confirms hit targets are comfortable, accidental taps are unlikely, press-and-hold timing feels deliberate but not slow, cancellation works, scrolling feels native, and dark-room readability is acceptable. |
